# Clinical Training Artifacts: AI Image Pipeline Storage After a 429 Rate-Limit Retry

Short answer: keep image generation, object-storage persistence, and retention as separate states in the queue; persist the generated bytes before acknowledging the render, retry a 429 with `Retry-After` or bounded exponential backoff, and derive the object key from an immutable tenant and job identifier. That design prevents a throttled upload from causing a second image generation, while the tenant boundary remains explicit in every storage operation.

This is a runbook for a healthtech team storing AI-generated images used in training artifacts. The image itself may be disposable, but the artifact record is not: a reviewer must be able to identify its tenant, reproduce the retention decision, and tell the difference between “rendered” and “available.” A successful model response is not a successful storage workflow.

## A governance contract for clinical training artifacts

The misleading symptom is simple: an image was created, then the upload failed with HTTP 429. The dangerous response is to put the whole pipeline back on the queue. That repeats the expensive or nondeterministic generation step and can create two clinically confusing artifacts for one request.

Use a state transition instead:

`requested -> rendered -> persisted -> retained`

The `rendered` record needs a durable byte reference, a digest, media type, tenant ID, and job ID. The persistence worker can then retry the same bytes. A delivery that receives a 429 should release its worker slot and schedule a later attempt; sleeping in the worker makes a rate limit consume queue capacity twice. Respect a valid `Retry-After` value. If it is absent or unusable, use exponential delay with jitter and a maximum attempt count.

The key must encode the ownership boundary, for example `tenant/{tenantID}/training/{jobID}.png`, after validating both identifiers against a restricted character set. This is naming discipline, not authorization. The storage credential still needs a policy that prevents one tenant's worker from reading or overwriting another tenant's prefix, and the application must verify that the job's tenant matches the requested key before enqueueing persistence.

A Node.js queue, a Go worker, or a managed workflow can implement the same state machine. The queue is not the source of truth; the artifact record is. On duplicate delivery, the worker should inspect the record and either verify the existing object or perform the same deterministic write, never create a random second key.

## How should a Node.js image pipeline retry a 429 rate-limit upload?

The retry policy should be scoped to the persistence operation, not the complete AI image pipeline. The small Go example below shows the important control points: a tenant-scoped key, a bounded delay, no retry for a permanent client error, and a verification request after the write. The endpoint is intentionally an interface supplied by the storage adapter; the queue contract is the part that should stay stable when the backend changes.

```go
package main

import (
	"context"
	"crypto/sha256"
	"fmt"
	"io"
	"math/rand"
	"net/http"
	"strconv"
	"strings"
	"time"
)

type Artifact struct {
	TenantID string
	JobID    string
	Bytes    []byte
	Media    string
}

func retryDelay(header http.Header, attempt int, now time.Time) time.Duration {
	if raw := header.Get("Retry-After"); raw != "" {
		if seconds, err := strconv.Atoi(raw); err == nil && seconds >= 0 {
			return time.Duration(seconds) * time.Second
		}
		if when, err := http.ParseTime(raw); err == nil && when.After(now) {
			return when.Sub(now)
		}
	}
	base := time.Second << min(attempt, 5)
	return base + time.Duration(rand.Intn(500))*time.Millisecond
}

func min(a, b int) int {
	if a < b {
		return a
	}
	return b
}

func persist(ctx context.Context, client *http.Client, endpoint string, token string, a Artifact) error {
	key := fmt.Sprintf("tenant/%s/training/%s.png", a.TenantID, a.JobID)
	digest := fmt.Sprintf("%x", sha256.Sum256(a.Bytes))

	for attempt := 0; attempt < 6; attempt++ {
		req, err := http.NewRequestWithContext(ctx, http.MethodPut, endpoint+"/"+key, strings.NewReader(string(a.Bytes)))
		if err != nil {
			return err
		}
		req.Header.Set("Authorization", "Bearer "+token)
		req.Header.Set("Content-Type", a.Media)
		req.Header.Set("X-Artifact-Digest", digest)
		resp, err := client.Do(req)
		if err == nil && resp.StatusCode >= 200 && resp.StatusCode < 300 {
			resp.Body.Close()
			return verify(ctx, client, endpoint, token, key, digest)
		}
		if err == nil {
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
		}
		if err != nil || (resp.StatusCode == http.StatusTooManyRequests || resp.StatusCode >= 500) {
			if attempt == 5 {
				return fmt.Errorf("persistence retry budget exhausted: %w", err)
			}
			var headers http.Header
			if resp != nil {
				headers = resp.Header
			}
			timer := time.NewTimer(retryDelay(headers, attempt, time.Now()))
			select {
			case <-ctx.Done():
				timer.Stop()
				return ctx.Err()
			case <-timer.C:
			}
			continue
		}
		return fmt.Errorf("permanent persistence status: %s", resp.Status)
	}
	return fmt.Errorf("unreachable")
}

func verify(ctx context.Context, client *http.Client, endpoint, token, key, expected string) error {
	req, err := http.NewRequestWithContext(ctx, http.MethodHead, endpoint+"/"+key, nil)
	if err != nil {
		return err
	}
	req.Header.Set("Authorization", "Bearer "+token)
	resp, err := client.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	if resp.StatusCode < 200 || resp.StatusCode >= 300 {
		return fmt.Errorf("verification status: %s", resp.Status)
	}
	if got := resp.Header.Get("X-Artifact-Digest"); got != expected {
		return fmt.Errorf("digest mismatch")
	}
	return nil
}
```

In production, the adapter should make the key path safely and the database transaction should record `persisted` only after verification. The code does not make a tenant boundary by itself; it gives the policy a stable value to authorize and audit. Keep the source bytes until that transaction commits. Then a retention worker may delete the temporary source according to the artifact's recorded policy, while a failed attempt remains replayable without rerunning generation.

## A capacity budget makes throttling visible

Queue depth is a weak signal. I would page on the age of the oldest `rendered` artifact and on the gap between rendered and persisted counts, with separate dimensions for tenant. Those measurements map to the delivery SLO and expose noisy-neighbor behavior that a global average hides. Record retry count, 429 count, time spent waiting, bytes awaiting retention, and verification failures; keep the request ID and tenant ID in structured logs without placing image content or prompts in them.

Capacity planning is equally plain. If render admission can produce bytes faster than the storage adapter can persist them, backoff only changes the shape of the queue. Use a per-tenant concurrency limit, a global storage budget, and admission control that defers new renders when the oldest persistence job approaches its page threshold. A retry budget is part of the SLO design: after exhaustion, mark the artifact `persistence_pending` for operator review and retain the bytes, rather than reporting a completed training artifact.

The operational choice is a buy-vs-build decision about control and on-call work, not a claim that one backend is universally better:

| Choice | Useful when | Cost or limitation |
| --- | --- | --- |
| Managed object storage | The team needs durable storage and lifecycle controls without operating disks | Provider policy, egress, and API differences still need testing |
| Self-hosted object storage | Data placement and direct operational control outweigh the platform team's maintenance load | The team owns upgrades, replication, capacity, and incident response |
| A storage abstraction in-house | Several backends must share tenant, digest, retention, and verification rules | The abstraction becomes another component to test and operate |

Do not choose based on a transient unit price. The meaningful comparison is whether the option can meet the tenant-isolation, retention, recovery-time, and audit requirements with the people available to page. I'm not sure any generic compatibility claim answers that; a failure-injection test against your exact policy does.

## Recovery checks, rollback, and the case for a different design

Verification should exercise the same identity that the application will use later: tenant, job, digest, media type, and retention deadline. Test duplicate deliveries, a 429 with and without `Retry-After`, a process restart during backoff, an object that exists under the wrong tenant prefix, and an exhausted retry budget. A successful write followed by a failed verification is still `persistence_pending`.

Rollback is a metadata operation first. Stop admitting new persistence work if the backend policy or credential is suspect, leave rendered bytes available, and replay only after authorization and capacity checks pass. Never compensate for an upload failure by regenerating an image unless the original bytes are irrecoverable and the product explicitly permits a different artifact.

The catch is that this runbook is not suitable when the storage system cannot enforce tenant-scoped authorization, cannot provide the metadata needed for verification, or cannot meet the required retention and audit controls. In that case, choose a backend or self-hosted design with those guarantees, even if it increases operational ownership. Stick with a simpler queue only when duplicate delivery, tenant isolation, and replay are already enforced elsewhere; otherwise the apparent simplicity moves the failure into the clinical record.
